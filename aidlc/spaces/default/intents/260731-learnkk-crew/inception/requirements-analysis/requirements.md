## Intent Analysis (의도 분석)

learnKK는 러닝 크루(learning crew — 특정 기간 특정 주제를 함께 학습하는 모임) 운영의 전 과정(개설 → 승인 → 모집 → 주차별 진행 → 출석 → 수료 판정 → 설문·피드백)을 **하나의 모바일 웹뷰 플랫폼**으로 통합하는 것을 목표로 한다. 현재 wiki 기반의 흩어진 수작업 운영을 대체하고, 관리자에게 전체 현황 모니터링·품질관리 수단을 제공하는 것이 핵심 가치다. [intent]

사용자가 이루려는 목표(기능이 아닌 성과):
- 모임이 학습 기간 내 정상적으로 진행되어 **수료로 이어지게** 한다 (멘토: 계획 주차 전부 진행·완료 / 멘티: 출석율 80% 이상 달성). [intent]
- 관리자가 4개 지점에서 품질을 통제하며 전체 모임을 감독한다. [decided]
- 학습/교육 프로그램 운영 방식을 검증하는 파일럿. [intent]

이번 워크플로우 성과물은 **상세 설계까지**(요구사항 → 유저스토리 → 애플리케이션/기능 설계 → NFR 요구)이며, 구현·배포·운영은 팀 3인의 개별 구현 워크플로우로 분리한다. [scope]

## 역할 (Roles)

- **멘토(mentor)** — 모임 개설·운영. 공지·자료·세션 진행, 멘티 피드백 확인. (모임 완료 인정 신청 단계 없음 — 관리자가 ③ 직접 처리) [intent][decided][rev-mk]
- **멘티(mentee)** — 모임 신청·참여·출석·과정 설문. [intent]
- **시스템 관리자(system admin)** — 4지점 승인(①개설 ②시작 ③모임완료(종료 시 직접) ④멘티수료), 모집 마감 확정, 전체 모니터링, 멘티 피드백 열람, 관리자↔멘토/멘티 쪽지. [decided][intent][Q2][Q8][rev-mk]

## Functional Requirements (기능 요구사항)

### FR1. 계정·프로필
- FR1.1 닉네임 + 비밀번호 + **사번(employee number)**으로 가입한다 — **가입 승인 절차 없음**. [scope][rev-us]
- FR1.2 비밀번호는 적응형 해시(bcrypt)로 저장한다. [decided][Mandated]
- FR1.3 프로필에 관심사 해시태그와 한 줄 소개를 둔다. [scope]
- FR1.4 중복계정 방지는 **사번 기반**으로 한다 — 하나의 사번당 하나의 계정만 허용(사번 유일성 검증). 기존 히든 IP 신호 방식을 **대체**한다. [rev-us] (project.md Decided의 "히든 IP 안티-중복" 결정을 사용자 게이트 수정으로 대체 — reconcile 필요)
- FR1.5 3역할(멘토/멘티/관리자)에 따른 역할 기반 접근이 적용된다. [intent]

### FR2. 모임 개설·승인
- FR2.1 멘토가 모임을 개설한다 — 주제, 학습기간, 모집기간, 정원, 진행방식, 학습자료, 공지, 그리고 **신청(사전) 설문 문항을 자유롭게 구성**. [scope][decided]
- FR2.2 관리자가 개설을 승인(①)하면 정식 모임으로 전환된다. [decided]
- FR2.3 모임은 상태를 가진다: 개설신청 → (①승인) 모집중 → (모집마감 확정) 시작대기 → (②시작) 진행중 → (③모임완료·④멘티수료) 완료. 반려/취소 경로 포함. [decided][Q2][assumption]

### FR3. 탐색·모집·신청
- FR3.1 멘티가 모임 목록을 탐색한다. [scope]
- FR3.2 멘티가 모임에 신청한다(선착순). 사전설문 응답은 신청 시점이 아니라 **관리자 ②시작 승인 이후** 진행한다(신청과 분리). [scope][rev-us] (project.md Decided의 "멘티는 신청 시 설문 응답" 결정을 게이트 수정으로 대체)
- FR3.6 멘티가 **②시작 승인 이후** 멘토가 구성한 사전설문에 응답한다. 멘토·관리자는 응답을 열람한다. [rev-us]
- FR3.3 모집은 **선착순 접수**로 정원까지 받는다. [Q2]
- FR3.4 **모집 마감 시 시스템 관리자가 모집을 확정**한다. 정원 미달인 경우 진행/취소 여부도 관리자가 결정한다. [Q2]
- FR3.5 멘티는 **모집 기간 중 신청을 취소**할 수 있다. 모임 시작(②) 이후에는 이탈할 수 없으며, 이후 수료 판정은 출석율로만 이루어진다. [Q3]

### FR4. 주차별 진행 (자료·공지)
- FR4.1 자료실은 **게시글(post) 형태**다 — 멘토가 주차(week session)별로 게시글을 작성한다. 게시글은 **본문 텍스트** + **선택적 파일 첨부(0개 이상)**로 구성되며, 파일 없이 글만 남기는 것도 가능하다. [scope][rev]
- FR4.2 게시글 본문과 메타데이터(작성자·주차·작성시각)를 저장한다. [scope][rev]
- FR4.3 첨부 파일은 문서 위주(PDF/이미지/오피스 등)이며 **파일당 크기 상한**을 둔다(기본값 제안 20MB, 최종 상한은 functional-design에서 확정). [Q4][assumption]
- FR4.4 첨부 파일은 **PostgreSQL(BLOB)에 직접 저장**하고 파일 메타데이터(파일명·형식·크기·업로더·소속 게시글/주차)를 함께 관리한다. [Q4]
- FR4.5 멘토가 공지사항을 게시한다. [scope]

### FR5. 쪽지 (메시징)
- FR5.1 멘토↔멘티, 관리자↔멘토/멘티 간 쪽지를 주고받는다. [scope]
- FR5.2 전달은 **인앱 확인 방식**(접속 시 목록/미확인 뱃지, 폴링/새로고침으로 갱신)이며 푸시·이메일·SMS는 두지 않는다. [Q5]
- FR5.3 쪽지 기능은 개발 난이도·아키텍처 영향이 낮을 경우 채팅형(대화 스레드) 방식으로 전환하는 것을 검토할 수 있다 — **미확정 설계 여지**. [Q5][assumption]

### FR6. 세션 일정·출석
- FR6.1 멘토가 주차별 **수업 세션의 날짜·시간을 지정**하고 멘티에게 공유한다. 한 주차에 **여러 세션**이 있을 수 있고, 지정한 날짜·시간은 **유동적으로 변경**할 수 있다(변경 시 멘티에게 반영). [rev-us] (OQ6 해소: 주차=일정 기반)
- FR6.2 관리자 ②시작 승인 이후, 각 세션의 예정 시간이 되면 **멘티에게 시스템 팝업이 제공**되고 멘티가 **직접 출석 체크(self check-in)**한다. [Q1][rev-us]
- FR6.3 각 멘티의 출석율 = (출석한 세션 수) / (**전체 예정 세션 수**). 80% 수료 판정(FR7.1)의 분모는 전체 예정 세션 수다. [rev-us] (RQ2=A)

### FR7. 수료 판정·완료
- FR7.1 멘티 수료는 출석율 **80% 이상**을 시스템이 자동 판정하고, 관리자가 승인(④)하여 확정한다. [decided][intent]
- FR7.2 전 세션 종료 시 **관리자가 모임 정상 완료(③)를 직접 처리**한다 — 멘토의 완료 인정 신청 단계는 없다. 멘토는 멘티 수료를 판정하지 않는다. [decided][rev-mk] (project.md Decided의 "멘토 완료 인정 신청" 결정을 refined-mockups 단계 사용자 수정으로 대체)
- FR7.3 멘토 성공 기준 = 계획된 주차별 모임을 전부 진행·완료. [intent]

### FR8. 과정 설문·피드백
- FR8.1 멘티가 과정 설문(피드백)을 제출한다. [scope]
- FR8.2 멘토가 멘티 피드백을 확인하며, 시스템 관리자도 열람할 수 있다. [decided]

### FR9. 관리자 모니터링
- FR9.1 관리자 대시보드는 **핵심 운영 현황**을 제공한다: 전체 모임 목록·상태, 4지점 승인 대기 큐(①②③④), 모임별 출석율·수료 진행 현황. [Q8][intent]
- FR9.2 집계 지표(개설 대비 승인 수, 모집 충족률, 평균 출석율·수료율)와 보조 지표(만족도, 멘토 재개설률)는 **이번 설계 범위에서 TBD로 이월**한다. [Q8]

## Non-Functional Requirements (비기능 요구사항)

- NFR1 **플랫폼** — 모바일 웹뷰 우선(최신 모바일 크롬/사파리 기준), 다른 환경 미고려. [intent][Q7]
- NFR2 **규모(설계 목표)** — 소규모 파일럿: 동시 사용자 수십 명, 진행 중 모임 수십 개 수준을 무리 없이 처리하도록 설계. [Q6]
- NFR3 **성능(가이드)** — 일반 화면·목록 응답 체감 1~2초 이내를 목표(엄격 SLA 아님). [Q6]
- NFR4 **가용성/복구** — 로컬 단일 인스턴스 전제. HA·다중화·백업 자동화는 이번 범위 밖(후속 워크플로우). [Q6][scope]
- NFR5 **데이터 보존** — 모임/세션/출석/수료 기록은 영속 보관. 중복방지는 사번 유일성으로 처리하므로 별도 히든 신호 보관·파기 정책은 불요. [Q6][rev-us]
- NFR6 **보안** — 최소 수준: 비밀번호 bcrypt 해시, 역할 기반 접근, 시크릿 비커밋, 안티-중복 신호 목적 한정·비노출. 전부 로컬, 외부 SaaS·클라우드 미사용. practices-discovery의 Security Posture(정적분석·의존성 스캔 등)를 상속한다. [decided][Mandated][Forbidden][team-practices]
- NFR7 **접근성/언어** — 한국어 단일. 접근성은 기본 준수 지향(폼 라벨·색 대비·키보드 포커스 등 상식 수준)이며 공식 WCAG 등급 인증은 목표가 아니다. [Q7]
- NFR8 **아키텍처 경계** — API JSON은 camelCase 통일, JPA는 snake_case 물리 네이밍, Entity를 API 경계에 비노출, 전역 에러 스키마 `{code,message,details}`. team-practices Code Style/Security Posture에서 확정된 경계 규약을 요구사항으로 승계한다. [Mandated][Forbidden][team-practices]

## Constraints (제약)

- C1 스택 고정: React(FE) + Java Spring(BE) + PostgreSQL(DB), 전부 로컬. [decided][Mandated]
- C2 외부 SaaS·클라우드·SSO·외부 연동 미사용. [Forbidden][scope]
- C3 이번 워크플로우 범위 = 설계까지. 실제 구현 코드·배포·CI·운영 인프라는 out of scope. [scope][Forbidden]
- C4 모바일 웹뷰 우선. [intent]
- C5 사용자 노출 텍스트는 한국어, 기술 용어·고유명사는 영어 유지. [Mandated]

## Assumptions (가정)

- A1 자료 첨부 파일 상한 기본 제안은 20MB이며 functional-design에서 최종 확정한다. [Q4]
- A2 모집 마감 시 관리자 확정(FR3.4)은 기존 4지점 승인 모델에 더해지는 액션으로, **정식 5번째 승인 지점으로 편입할지 여부는 functional-design에서 정합화**한다. [Q2]
- A3 쪽지→채팅형 전환(FR5.3)은 구현 난이도·아키텍처 영향 평가 후 결정하는 설계 여지이며, 기본 가정은 인앱 쪽지다. [Q5]
- A4 (해소) 중복방지는 사번 유일성 기반으로 변경됨(FR1.4) — 기존 히든 IP 신호 저장/보관 가정은 폐기. [rev-us]
- A5 사번의 형식·유일성 검증 규칙(예: 자릿수·조직 범위)은 functional-design에서 확정. [rev-us]
- A6 세션 날짜·시간 변경의 통지 방식(인앱 현황 반영)·과거 세션 편집 제약은 functional-design에서 확정. [rev-us]

## Out of Scope (명시적 제외)

- 실제 구현 코드, 배포·CI·운영·모니터링 인프라. [scope]
- 게이미피케이션(스트릭·뱃지), 결제·정산, 외부 시스템 연동·SSO. [scope]
- 프로필 고도화(관심사 기반 추천 등), 과정/멘토 피드백 리포트 상세화. [scope]
- 관리자 대시보드 집계·보조 지표 산출(FR9.2) — 이번 설계에서 TBD 이월. [Q8]
- 데스크톱 등 모바일 웹뷰 외 환경. [intent]
