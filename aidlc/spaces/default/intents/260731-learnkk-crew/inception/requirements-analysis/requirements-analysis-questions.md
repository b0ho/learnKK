## Q1. 출석 기록 방식 + 수료 분모 (80%의 기준)
"모임 시작/종료 + 멘티 출석 체크"가 구체적으로 어떻게 동작하나요?
- A. 멘토가 주차별 모임을 시작(②관리자 승인 후)하면 출석 창이 열리고, **멘티가 스스로 출석 체크(self check-in)**, 멘토가 종료. 수료 분모 = **계획된 전체 주차 수**
- B. **멘토가 출석부에서 멘티별 출석/결석을 직접 표시**(멘티 self check-in 없음). 분모 = 전체 주차 수
- C. 자동 — 멘티가 해당 주차 콘텐츠(자료/공지) 열람 또는 접속 기록으로 출석 간주. 분모 = 전체 주차 수
- D. A + 지각/사유결석 등 상태 구분 포함
- X. 기타 (직접 서술)

[Answer]:a

## Q2. 모집 정원 처리 (신청이 정원을 넘거나 못 채울 때)
- A. **선착순** — 정원까지 신청 즉시 확정, 초과분은 마감. 모집기간 종료 시 미달이어도 **모임은 그대로 진행**
- B. 선착순 확정 + 미달 시 **멘토가 진행/취소 선택**
- C. **멘토가 신청자(사전설문 응답 포함) 중 선발** — 선착순 아님, 정원 내 승인
- D. C + 미달 시 멘토가 진행/취소 선택
- X. 기타 (직접 서술)

[Answer]:선착순으로 받되, 마감일에 시스템 담당자가 확정. 이때 미달시 진행 여부도 담당자가 확정

## Q3. 멘티 중도 이탈/신청 취소
- A. 모집기간 중 **신청 취소 가능**, 모임 시작(②) 이후에는 이탈 불가(출석률로만 수료 판정)
- B. 시작 이후에도 **중도 포기 가능** — 포기 시 수료 대상에서 제외(분모에서 제거)
- C. 시작 이후 중도 포기 가능하되, 분모는 전체 주차 유지(사실상 미수료 처리)
- D. 취소/이탈 개념 없음 — 신청=끝까지 참여 가정 (이번 설계 범위 밖)
- X. 기타 (직접 서술)

[Answer]:a

## Q4. 자료실 파일 업로드 (형식·크기·저장 위치)
전부 로컬 환경 전제입니다.
- A. 문서 위주(PDF/이미지/오피스 등) + **파일당 상한(예: 20MB)**, 저장은 **로컬 파일시스템 경로 + DB에 메타데이터**
- B. A와 같되 저장을 **DB(BLOB)** 에 직접
- C. 링크(URL) 첨부만 — 실제 파일 업로드 없음
- D. 파일 업로드 + 외부 링크 둘 다 허용
- X. 기타 (형식/상한/저장 방식 직접 서술)

[Answer]:b

## Q5. 공지·쪽지의 전달 방식 (실시간성)
전부 로컬·모바일 웹뷰 전제입니다.
- A. **인앱 확인만** — 접속 시 목록/뱃지로 확인(푸시·이메일·SMS 없음). 새 항목은 폴링/새로고침으로 반영
- B. 인앱 + **웹 실시간 갱신(WebSocket/SSE)** 으로 즉시 표시
- C. 인앱 + 브라우저 웹푸시 알림
- X. 기타 (직접 서술)

[Answer]:a, 쪽지 기능은 채팅과 비교해서 개발 난이도 및 현재 아키텍쳐에서 크게 영향 없는 경우 낮은 경우 채팅으로 전환 고려

## Q6. NFR 자세 — 이 로컬 MVP 설계가 겨냥할 규모/목표 (해당되는 것 모두 선택 가능)
설계 전용이라 실측은 없지만, 설계가 겨냥할 목표치는 정해야 합니다.
- A. **소규모 파일럿 규모** — 동시 사용자 수십 명, 진행 중 모임 수~수십 개 수준을 무리 없이 설계 목표로
- B. 성능 목표 = 일반 화면/목록 응답 **체감 1~2초 이내**(엄격 SLA 아님, 가이드)
- C. 가용성/복구는 로컬 단일 인스턴스 전제 — HA·다중화·백업 자동화는 이번 범위 밖(후속 워크플로우)
- D. 데이터 보존: 모임/출석/수료 기록은 영속 보관, 안티-중복 신호만 보관창 후 파기(이미 확정)
- X. 기타 (구체 목표치 직접 서술)

[Answer]:a, b, c, d
