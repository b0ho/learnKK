## 의존 매트릭스 (행 → 열: 행이 열의 Service에 의존)

표기: `Y`=런타임 쓰기/집행 의존, `R`=읽기 전용(read port로 해소, 아래 검증 참조), `-`=자기 자신.

- **C0(Shared Kernel)**: 전 모듈이 의존(타입·enum·에러). 아무 모듈에도 의존하지 않음(리프).
- **의존 방향:** 협력 모듈 → 기반 모듈. C1(인증·사용자)·C2(모임)가 널리 참조되는 기반. **쓰기(Y) 의존은 비순환 DAG**; 일부 read(R) 상호참조는 read port로 해소(아래).

## 순환 의존 검증

- **쓰기(Y) 전이 순환 없음.** 상태 전이의 단일 소유(모임 SM=C2, 멘티 수료=C4)라 쓰기 방향은 DAG. 검증은 아래 read(R) 상호참조 2건에 집중한다.
- **R-1) C2↔C3 (신청자·정원 read 상호참조).** C2(멘토 운영 허브 US-2.3)는 신청자 목록을 보이려 C3.listApplicants를 read; C3(신청 US-3.2)는 모집중 상태·정원을 C2에서 read. 둘 다 read이고 쓰기 전이는 C2 단일 소유라 **쓰기 순환 없음**. 컴파일-레벨 순환 회피책: (a) 프론트 단일 API client가 `listMyMeetings`(C2)+`listApplicants`(C3)를 **컨트롤러/클라이언트 레벨에서 조합**하면 백엔드 서비스 순환 자체가 불필요, 또는 (b) **공유 read 포트**(인터페이스)로 분리. → ADR-007.
- **R-2) C2↔C4 (③완료 전제조건 read).** ③완료(US-7.3)는 "전 세션 종료" 전제조건을 요구하는데, 이 사실은 **세션 소유자 C4의 상태**다. 따라서 완료 처리 흐름은 C4(SessionService)의 "전 세션 종료 여부"를 **read**해야 한다 → **C2→C4 read**(기존 C4→C2 상태 read와 합쳐 read 상호참조). **집행 위치 확정:** 전제조건 검증은 **관리자 완료 오케스트레이션(app-service/Controller 계층)** 이 C4를 read해 확인한 뒤 `MeetingApprovalService.completeMeeting(...)`을 호출하는 방식(또는 C2가 **C4 read 포트**에 의존)으로 처리한다. 쓰기 전이(완료 상태 기록)는 여전히 C2 단일 소유 → **쓰기 순환 없음**. → ADR-007(범위에 C2↔C4 포함).
- **결론:** 쓰기 전이 순환 없음. read 상호참조 2건(C2↔C3, C2↔C4)은 컨트롤러 조합 또는 공유 read 포트로 해소 — 물리 배치는 functional-design/units-generation 확정(ADR-007). "C2→C4 없음/단방향" 이전 서술은 **정정**됨(위 R-2).

## 공유 리소스

- **C0 Shared Kernel**: 도메인 타입·enum·에러 스키마·RBAC 역할 — 컴파일 타임 공유(순환 아님, 리프).
- **PostgreSQL**: 단일 DB, 모듈별 테이블 소유. 교차 조회는 소유 모듈 Service 경유(직접 테이블 접근 금지).
- **인증 컨텍스트(Principal)**: C1이 발급, 전 Controller가 세션 검증 후 주입(횡단).

## 통신 패턴 요약

- 전부 **인-프로세스 동기**(모듈 Service 호출). 이벤트/큐 없음(Q3).
- 클라이언트↔백엔드만 네트워크(동기 REST/JSON, OpenAPI #1).
