## Contribution

렌즈: 구현가능성 · 스토리 사이징(INVEST) · 계약/의존성 검증. 전부-로컬 React+Spring+PostgreSQL, monorepo, 3인 독립 병렬 슬라이스 전제. 슬라이스 배분의 근거가 되므로 사이즈·의존·계약 고정 지점을 우선 검증했다.

### 1. 사이즈 위반 — 분리 권고 (INVEST "Small/Independent")

- **US-2.1 (멘토 모임 개설) 과대.** 한 스토리가 (a) 모임 기본정보(주제·기간·정원·진행방식) + 주차수 파생, (b) 학습자료/공지 초기값, (c) **사전설문 문항 빌더(동적 폼 구성)** 를 모두 묶는다. 사전설문 빌더는 자체 스키마(질문 테이블 + 응답 테이블)와 검증 로직을 가진 독립 서브도메인이며, US-3.2(신청+설문 응답)가 **바로 이 부분에만** 의존한다. 분리 권고:
  - **US-2.1a** 모임 기본정보 개설(+계획 전체 주차 수 파생, FR6.3 분모 확정) — Must
  - **US-2.1b** 사전설문 문항 빌더 구성 — Must
  - 효과: US-3.2 의존 대상이 US-2.1a 전체가 아닌 US-2.1b로 정밀해지고, "메일 생성이 설문 구성+주차수 파생을 번들"하는 전형적 과대 스토리가 해소된다.

- **US-4.1 (주차 게시글 본문+선택 첨부) 과대.** 본문 CRUD와 (BLOB 업로드 + 멀티파트 처리 + 크기 상한 검증 + 파일 메타데이터 관리)는 테스트 경계·리스크가 다르다. 분리 권고:
  - **US-4.1a** 주차 게시글 본문 작성·조회(첨부 0개) — Must
  - **US-4.1b** 파일 첨부 업로드·PostgreSQL(BLOB) 저장·크기검증·메타데이터 — Must
  - 효과: 첨부 없는 게시글 경로(요구사항 [rev]로 명시된 핵심)가 첨부 기능과 독립 배포·테스트 가능. US-4.2 열람은 4.1a(본문)만으로도 성립.

- 분리 후 스토리 수: 기존 ~24개 → ~26개. **여전히 medium granularity(20–30) 범위 내**로 일관성 유지.

### 2. 의존성 결함

- **US-6.1 의존성 라벨 오류(반드시 정정).** "의존성: US-7.x(②승인, 아래 US-6.3), US-2.2"로 적혀 있으나 ②승인은 **US-6.3**이다. `US-7.x` 참조는 오기로, 그래프에 없는 dangling 참조다. → `의존성: US-6.3(②승인), US-2.2`로 정정.
- **그래프 비순환성은 확인됨.** US-1.1 → US-2.1 → US-2.2 → US-3.1 → US-3.2 → US-3.4 → US-6.3 → US-6.1 → US-6.2 → US-7.1 → US-7.2, US-7.3(→US-6.1), US-9.1/9.2(집계 대기). 사이클 없음. 정정 후 acyclic 유지.

### 3. 누락 선행조건 — 인증/세션/RBAC (가장 큰 구멍)

- **로그인·세션·역할기반 접근이 독립 스토리로 존재하지 않는다.** US-1.1은 가입 후 "로그인 상태가 된다"까지만 다루고, 재방문 로그인·세션 유지·로그아웃·FR1.5 RBAC 강제가 어느 스토리에도 없다. 그런데 **모든 역할 액션(US-2.x~US-9.x)이 인증 세션과 역할 판별을 암묵 전제**한다 → 숨은 전역 선행조건.
  - 권고: **US-1.0 로그인·세션·RBAC 경계** 스토리 신설(닉네임/비밀번호 로그인, 세션 발급/만료, 403/401 역할 경계). Must, 의존성 US-1.1.
  - 이것은 team-practices의 **walking skeleton 공통 기반 3요소(인증 + 모임 도메인 + DB 스키마)** 중 "인증"이며, **사전 계약 #1(API 계약)의 인증/인가 엔드포인트**를 고정한다. 슬라이스 분기 전 반드시 확정되어야 한다.

### 4. Cross-slice 계약 고정 지점 (team-practices 3 사전 계약과 연결)

병렬 착수 전 고정해야 하는 공유 계약을 스토리에 매핑한다:

- **계약 #1 API/OpenAPI** — US-1.0(인증), 전역 에러 `{code,message,details}`(US-1.1에 이미 등장)이 스키마를 핀한다.
- **계약 #2 DB 스키마** — US-1.1(user), US-2.1a(meeting), US-2.1b(survey question), US-3.2(survey answer), US-4.1b(post_attachment BLOB+metadata), US-6.2(attendance)가 핵심 테이블을 핀한다. 이 6개가 스키마 계약 owner 후보.
- **계약 #3 도메인 타입** — **모임 상태 enum + 전이표(개설신청→모집중→시작대기→진행중→완료 + 반려/취소)와 멘티 수료 상태, 4승인 지점 enum**. 현재 이 상태머신이 US-2.2/US-3.4/US-6.3/US-7.2/US-7.3에 **분산**되어 있고 어느 단일 스토리도 canonical 정의를 소유하지 않는다. → **상태머신 정의를 명시적 공유 아티팩트로 승격**하고(스토리 노트 또는 functional-design owner 지정), 위 전이 스토리들이 이를 참조하도록 권고. 이 팀 최대 리스크(interface 불일치)의 직접 방지책.

### 5. MoSCoW ↔ 크리티컬 패스 불일치

- **US-3.4(모집 마감 확정)를 Should로 둔 것은 상태머신상 모순.** FR2.3상 `시작대기`는 오직 모집 확정으로만 도달하고, 그 뒤 ②시작→진행중→출석→수료로 이어진다. 즉 **Must인 US-6.3/6.1/6.2/7.1/7.2가 US-3.4에 전이적으로 의존**한다. Should로 낮추면 delivery-planning이 MVP에서 US-3.4를 드롭할 때 수료 여정(intent의 핵심 성과지표) 전체가 끊긴다. → **US-3.4를 Must로 승격**하거나, 최소한 "시작대기 전이는 하드 선행조건, MVP 드롭 불가"를 스토리에 명시.

### 6. 전부-로컬 스택 실현가능성 플래그

- **US-4.1b BLOB(20MB) 실현가능하나 스트리밍 주의.** PostgreSQL `bytea`로 저장 시 20MB × 다중 첨부를 JVM 힙에 통째로 로드하면 소규모라도 OOM 위험. 업로드/다운로드를 스트리밍(멀티파트 max-size = 앱 상한 정렬)으로 처리 권고. 파일럿 규모(동시 수십)엔 충분. functional-design에서 형식 화이트리스트·최종 상한 확정(OQ4).
- **US-6.1/6.2 출석 창 — 스케줄러 불필요(적합).** 멘토 수동 시작/종료 트리거의 boolean 상태 창이라 cron/배치가 필요 없어 로컬 단일 인스턴스에 정확히 맞는다. 단 **OQ6(주차=순번 vs 날짜)** 이 순번 단위로 확정되어야 시간기반 잡 도입을 피할 수 있다 — functional-design에서 순번 전제 확정 권고.
- **US-5.1 인앱 폴링** — 로컬·수십 명 규모에서 폴링 부하 무시가능. 실현가능. 채팅형 전환(OQ2)은 노트 유지 타당.
- **US-1.2(안티-중복 신호)** 는 저장형태·TTL이 OQ5/A4로 미확정이라 지금은 **Estimable 약함**. Must 유지는 동의하되, nfr-design 확정 전까지 사이징 잠정임을 노트로 명시 권고.

## Positions

- AGREE: 여정 기반 에픽 ①~⑨ + medium granularity(Q1/Q2=A) — FR 그룹 정렬이 슬라이스 배분에 깔끔하게 대응한다.
- AGREE: 4지점 승인을 각각 독립 스토리(Q4=A) — 트리거·상태전이가 달라 개별 테스트 가능, INVEST 부합.
- AGREE: 의존성 그래프는 (US-6.1 라벨 오기 정정 후) 비순환이며 여정 순서와 정합.
- OBJECT: US-2.1 과대 — 사전설문 빌더를 US-2.1b로 분리해야 US-3.2 의존이 정밀해지고 Small 충족.
- OBJECT: US-4.1 과대 — 본문(4.1a)과 BLOB 첨부(4.1b) 분리로 첨부 없는 게시글 경로를 독립 테스트/배포 가능하게.
- OBJECT: 인증/세션/RBAC 독립 스토리 부재 — 모든 역할 액션의 숨은 전역 선행조건이자 walking-skeleton 인증 기반. US-1.0 신설 필요.
- OBJECT: US-3.4 Should — 상태머신상 수료 여정의 하드 선행조건이라 Must여야 하거나 "MVP 드롭 불가" 명시 필요.
- OBJECT: US-6.1 의존성 `US-7.x` 오기 — `US-6.3(②승인), US-2.2`로 정정.
- OBJECT: 모임 상태머신(enum+전이표)이 스토리 전반에 분산 — 도메인 타입 계약(#3)의 단일 owner 아티팩트로 승격해 interface 불일치 리스크 차단.
